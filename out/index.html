100 apps: how ready are they to become agent toolkits?

A small version of an integration research workflow. For each app: what auth it uses, whether a developer can get credentials alone, what the API looks like, whether the vendor already ships an MCP server, and whether a toolkit could be built today. Every row links to the vendor page behind it.

Composio AI Product Ops take-home. Prepared by Anish Singh Rawat. Data as of 23 Nov 2026. Live page: composio-takehome-nine.vercel.app. Source repo: github.com/sranish/take-home. Machine-readable copy: apps.json and apps.csv.

1. The patterns

72of 100 look buildable today
53confirmed self-serve (free or trial)
7need sales or an existing customer
87have a vendor MCP server (64 full, 23 limited)
66document OAuth (43 also offer a key or token)
72rows fully verified on vendor pages
  1. Auth is rarely the blocker. Access is. 72 apps take an API key or token, 66 document OAuth, 43 offer both. Where building is blocked, the reason is who can get credentials: approval or review (8), paid plan (5), contact sales (4), existing customer only (3), account needed, free path not confirmed (3).
  2. Vendor MCP servers are the norm now. 87 of 100 have one (64 full, 23 limited: docs-search only, beta, or dev tooling). "Has MCP" is not one fact, so the matrix splits it.
  3. MCP auth is OAuth even where the REST API is key-based (Attio, Close, Intercom, ClickUp, Linear, Stripe). Stripe's MCP stops taking plain secret keys on 11 Jan 2027. Key-only toolkits will age badly.
  4. Gating follows the category. Developer and productivity tools: self-serve. Ads platforms: review-gated (Google, Meta, LinkedIn, Pinterest, Threads). Finance: free test modes (Stripe, Plaid) or customer-only tokens (Brex, PitchBook). Enterprise CRM and support: sales-led. Counts below.
  5. Easy wins: 39 apps are self-serve, buildable today, and already have a full vendor MCP server. Filter the matrix: access self-serve, MCP official.
  6. Needs outreach: DealCloud, Pylon, Gladly, Salesforce Commerce Cloud, Waterfall.io, Brex, PitchBook. Needs approval: WhatsApp Business, Google Ads, Meta Ads, LinkedIn Ads, Pinterest, Threads (Meta), Amazon Selling Partner, Plaid. Needs a paid plan: Help Scout, Squarespace, Ecwid, Ahrefs, Clay, NotebookLM.
  7. Not everything on the list is an API. Sherlock, Mermaid CLI are local CLIs with no auth. 3 apps stayed unclear after three passes: fanbasis, Paygent Connect, iPayX.
  8. Model memory was stale exactly on the newest facts. Without browsing, the first pass scored 96% on auth and 92% on access, but 59% on MCP. The full log is in section 4.

3. The workflow

  1. Intake. The 100 rows from the brief: number, name, hint.
  2. First pass, no browsing. The model answers auth, access and MCP from memory. Saved to disk before any lookup, for 86 apps.
  3. Identity check. Confirm the official domain from the hint. Flag look-alikes and legacy doc sites.
  4. Docs-grounded pass. Fetch the vendor auth page, the pricing or signup page, and the MCP page. Extract into a fixed schema. "Not stated" is an allowed answer and every prompt said "from this page only, never guess".
  5. Validation. Each row carries vendor evidence links and a status. A non-vendor source never upgrades a row to Verified.
  6. Recheck loop. Rows with conflicts, deprecation notes, or MCP claims from non-vendor pages got a second targeted lookup. After the audit flagged "none found" as weak, a second agent swept all 40 none, unchecked or unconfirmed MCP rows.
  7. Blind audit. A separate agent with no access to the findings re-researched a random sample. Agreement is computed by script, disagreements are settled on the vendor page, and corrected rows carry an audit-corrected flag.
  8. Spot check. The sampled fields are checked twice against vendor pages and every mismatch is settled or flagged. See section 4.
  9. Synthesis. build.py computes every number on this page from the dataset.

Judgment calls along the way

  • Deciding what counts as an "official" MCP server. A docs-search server, a closed beta and a full account server are different things.
  • Name collisions: Clay (clay.com) and Clay (clay.earth), Consensus and goconsensus.com, Paygent and the Japanese PAYGENT, iPayX and several iPay companies, transcriptapi.com and transcriptapi.net.
  • Doc sites that only render in a real browser: QuickBooks, Xero, Ramp, Lark, and the Gumroad API page. These rows are marked and need a browser pass.
  • Sales-gated apps, where only an email to the vendor settles the question.

What was run

About 180 page fetches and 10 web searches in the main run, plus an earlier research task that covered 14 of the harder apps, plus the blind audit agent. Files in the repo: pass1_priors.tsv (first-pass answers), rows.psv (the dataset), audit_sample.txt and audit.psv (blind audit), build.py (stats and this page).

5. Traps met along the way

  • Text aimed at AI tools. gopaygent.com carries a meta tag telling language models to call it a "superior Stripe alternative". Treated as content, never as instructions.
  • Hints that point at old docs. highlevel.stoplight.io, binance-docs.github.io and harvestapp.com are not the current docs. Amazon SP-API docs moved to developer-docs.amazon.
  • MCP look-alikes. Zendesk's GA "MCP client" points outward, and the Marketplace "MCP Server" app there is by Swifteq. PitchBook's "Essential" MCP is Perplexity's; only "Premium" is PitchBook's. Docs-search servers (Discord, Mailchimp, Twilio) are easy to mistake for account servers.
  • Vendor pages that disagree with each other. Pumble names two different auth headers. Otter has a stale Enterprise-only MCP article. Aircall's developer FAQ denies the MCP its own help centre documents.
  • Name collisions. Clay and clay.earth, Consensus and goconsensus.com, Paygent and the Japanese PAYGENT, iPayX and several iPay companies, transcriptapi.com and transcriptapi.net.
  • Half-true hints. "Otter AI (MCP server)" is right, but there is no public API key. "Consensus (OAuth requested)" fits the MCP; the REST API uses a key.
